
> 火焰图展示的是“采样时，程序经常停留在哪条调用栈上”，不是代码执行的时间顺序，也不直接等于 CPU 或 NPU 利用率。

## 一、先认识坐标

你的 py-spy 图是从上往下展开的：

```text
all
└── process
    └── thread
        └── execute_model
            └── model.forward
                └── attention
                    └── synchronize / replay
```

- 纵向：调用关系。越往下，调用越深。
- 横向宽度：该函数及其子函数被采样到的次数。
- 横向位置：通常没有时间意义，只是把不同调用分支排在一起。
- 颜色：py-spy 中主要用于区分方块，不表示红色更慢或绿色更快。

有些标准火焰图是从下往上展开的，判断方式很简单：找到 `all`、进程或线程所在位置，那一层就是根。

## 二、宽度到底代表什么

假设看到：

```text
execute_model                 4000 samples
└── model.forward             3800 samples
    └── attention             1800 samples
```

含义是：

- 4000 次采样时，调用栈包含 `execute_model`。
- 其中3800次深入到了 `model.forward`。
- 其中1800次深入到了 `attention`。

不能把三者相加，因为它们是父子关系，同一份样本会同时出现在多层：

```text
错误：4000 + 3800 + 1800
正确：attention 是 execute_model 内部的一部分
```

父函数很宽，不代表父函数本身慢；真正时间可能都花在它下面的子函数中。

## 三、必须区分“全局占比”和“进程内占比”

你的图使用了：

```text
--subprocesses
```

因此12,490个总样本来自三个进程：

| 进程 | 样本数 | 全局占比 |
|---|---:|---:|
| EngineCore | 4,301 | 34.44% |
| Worker_TP0 | 4,096 | 32.79% |
| Worker_TP1 | 4,091 | 32.75% |

这里的34%不是“EngineCore 占用了34% CPU”。三个进程是同时被采样的，样本数接近很正常。

分析某个进程时，要重新计算进程内占比。例如 TP0：

```text
model_runner.execute_model = 3860 samples
TP0 总样本               = 4096 samples

3860 / 4096 ≈ 94.2%
```

所以图中显示的全局占比30.9%，换算到 TP0 内部其实是94.2%。

以后看到多进程火焰图，第一步一定是：

> 先按进程切开，再在每个进程内部分析。

## 四、重点寻找“宽叶子”，而不只是“宽父节点”

可以把方块分为两类：

- 宽父节点：表示整条业务路径，例如 `execute_model`。
- 宽叶子节点：调用栈在这里结束，通常更接近真正耗时的位置。

例如：

```text
execute_model
└── forward
    └── attention
        └── synchronize
```

如果 `execute_model` 很宽，但几乎全部进入 `synchronize`，真正值得研究的是同步，而不是 `execute_model` 这个包装函数。

不过要特别注意：普通 py-spy 只能看到 Python 栈。一个函数成为“叶子”，也可能是因为它下面进入了 py-spy 看不到的 C++、torch-npu 或 ACL 代码，不一定是 Python 本身正在计算。

## 五、常见函数应该怎么判断

| 火焰图函数 | 第一反应 | 需要进一步确认 |
|---|---|---|
| `execute_model`、`forward` | 正常模型执行主路径 | 看更深层的 Attention、算子和同步 |
| `wait_for_response`、`_recv` | 等其他进程或 worker | 可能完全正常，不一定是瓶颈 |
| `_worker` | 线程池工作循环 | 必须看子栈，单独出现通常没有意义 |
| `sched_yield` | 轮询时主动让出 CPU | 结合 `top` 判断是否真的消耗 CPU |
| `synchronize` | 主机等待 NPU stream 完成 | 可能是 NPU 正在计算，不等于 CPU 瓶颈 |
| `replay` | 执行或提交 ACL Graph | 普通 py-spy 看不到图内 NPU kernel |
| `torch/_ops.py:__call__` | 进入 PyTorch 自定义算子 | 用 `--native` 或 NPU profiler 展开 |
| `attention_v1.py` | Attention 执行上下文 | 可能包含算子提交、设备执行和同步 |
| sampler | Token 采样 | 占比大时才考虑采样瓶颈 |

所以，“等待函数很宽”不能直接下结论。先问：

1. 它在等谁？
2. 等待期间 CPU 是否繁忙？
3. 等待期间 NPU 是否在运行？
4. 这是正常的父进程等待，还是不必要的同步？

## 六、如何识别 TP 是否失衡

并排比较 `TP0` 和 `TP1`：

- 总样本数是否接近。
- `execute_model` 占比是否接近。
- 模型 forward 是否接近。
- 是否一个 rank 长时间停在通信或同步，另一个 rank 正在执行算子。

你的图里：

```text
TP0 = 4096 samples
TP1 = 4091 samples
```

总体非常接近，因此没有明显的整体失衡。

不过内部状态存在差异：

- TP0 更多停留在 `synchronize`。
- TP1 更多停留在 `aclgraph.replay`。

这只能说明采样时两个 rank 所处阶段不同，不能单凭这一点判定 TP0 性能异常。因为 TP0 的 `synchronize` 可能正在等待已经提交到 NPU 的任务完成。

## 七、普通版、native版和NPU分析的边界

### 普通 py-spy

```bash
py-spy record --pid <EngineCore_PID> \
  --subprocesses --rate 20 --threads \
  -o normal.svg
```

适合回答：

- 哪个 Python 进程在工作。
- 哪条 Python 调用路径最宽。
- 是模型执行、调度、采样还是进程等待。
- 两个 TP worker 是否明显失衡。

### native版

```bash
py-spy record --pid <EngineCore_PID> \
  --subprocesses --rate 20 --threads --native \
  -o native.svg
```

适合回答：

- Python 下面进入了哪些 C/C++ 函数。
- torch-npu、ACL、通信库的宿主机调用栈。
- Python 叶子下面是否隐藏了大量原生执行。

### NPU profiler

适合回答：

- 哪个 NPU kernel 最慢。
- NPU 是否存在大段空洞。
- 算子之间是否提交不及时。
- HCCL 通信占用了多少时间。
- `synchronize` 等待期间 NPU 到底在执行什么。

因此：

> py-spy 负责看主机调用栈，msprof 等工具负责看设备时间线。两者不能互相替代。

## 八、以后按这个顺序读图

1. 看生成命令：是否有 `--subprocesses`、`--native`、采样率和采样时间。
2. 看根节点：包含哪些进程和线程。
3. 按进程归一化：不要只看全局百分比。
4. 找业务主干：例如 `execute_model → forward → attention`。
5. 找宽叶子：同步、原生算子、通信、采样还是等待。
6. 比较并行进程：TP0/TP1 是否对称。
7. 区分计算与等待：等待期间 CPU/NPU 是否真的空闲。
8. 用其他监控验证：`top`、GIL、NPU利用率、msprof。
9. 对比实验必须保持相同负载：相同模型、请求、并发、输出长度和预热状态。

最后记住三个最容易犯的错误：

- 不要把父子方块的百分比相加。
- 不要把方块宽度直接当成 CPU 利用率。
- 不要把普通 py-spy 的 Python 叶子直接认定为 Python 性能瓶颈。
